# CaseLens — Design notes

CaseLens is an enterprise customer-support intelligence platform: hybrid RAG
over help-desk tickets plus a semantic SQL layer, charted with Plotly and
answered by a LangGraph agent that is grounded against tool output.

The full, phase-by-phase build instructions live in `CaseLens.md`. This file
captures the design decisions the document asks you to make explicit.

## Key decisions

1. **The LLM never writes numbers.** Numbers come from SQL results. The agent
   calls `analytics_query(metric, dimension, ...)` with names from a YAML
   whitelist, and a verifier checks every number in the final answer against
   tool output.
2. **Semantic layer over free-form text-to-SQL.** SQL is generated by
   deterministic code from whitelisted identifiers, bound parameters, a
   read-only role, a statement timeout, and a row cap. Free-form SQL is an
   optional guarded fallback, disabled by default.
3. **Charts are built from stored DataFrames.** The model sends a `ChartSpec`;
   the backend validates columns and builds the Plotly figure in Python.
4. **Hybrid retrieval, measured not assumed.** Dense, BM25, RRF, +rewrite,
   +expansion, and +rerank are each an ablation in the evaluation.
5. **Parent–child documents.** Small child chunks (utterances) are searched;
   parent ticket facts come from Postgres at context-assembly time.
6. **Honest coverage.** Conversation coverage is computed from the database and
   injected into prompts; the system says "not available" rather than inferring.
7. **Evidence has IDs.** Retrieval evidence is `E1…En`; analytics results are
   `D1…Dn`. Answers cite them; the UI links them to the source.
8. **Idempotent everything.** File-hash-gated ingestion, deterministic UUIDv5
   point IDs, content-hash-gated re-indexing.

## Data mapping decisions (Phase 3)

The profiling step produces `data/processed/profile_report.md`. Answer these six
questions and then fill `configs/column_map.yaml` with the real CSV headers:

1. Which column is the ticket primary key in `issues.csv`? Is it unique and the
   same key used in history, snapshot, and utterance files?
2. Which columns hold category, priority, project, status, created/resolved
   timestamps? What timestamp formats and timezones?
3. How are history rows structured (one row per change? field name + old/new)?
4. What does `sample_utterances.csv` contain — speaker role, text, ordering,
   timestamp? What fraction of tickets have utterances?
5. Is any customer/product/country information actually present? If not, the
   system must say so and never infer it.
6. Is there a country field that joins to `holidays_by_country.csv` (which
   determines whether business-hours resolution time is possible)?

## Architecture

React UI → FastAPI → LangGraph agent → tools
(`analytics_query`, `search_tickets`, `render_chart`, `get_ticket`,
`get_ticket_history`) → PostgreSQL (structured facts, `ticket_facts`
materialized view) and Qdrant (dense BGE-M3 + BM25 sparse vectors).

## Extending to other sources

`ingestion/adapters/base.py` defines the canonical `Batch` contract. A
`zendesk.py` adapter only needs to implement `extract()` and emit the same
batches; nothing downstream changes.

## Non-goals (deliberate)

Authentication, multi-tenancy, PII redaction, observability, and queueing the
LLM are out of scope for this iteration. The hooks where they would land are
named here so they are easy to add later.
